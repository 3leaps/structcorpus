# ADR-0002: Python 3 standard library for corpus tooling and generators

## Context

Corpus tooling validates metadata, hydrates generated inputs, and verifies
hashes. It has to run for the people who use the corpus: parser and binding
authors working in Rust, Go, TypeScript, Python, C, Java, and other languages.
Asking them to install a toolchain just to read fixtures is a barrier, and
every third-party dependency becomes a supply-chain surface in a repository
whose job is to be trusted test material.

Candidates considered:

| Option | Availability | Exact arithmetic | Dependency surface |
| --- | --- | --- | --- |
| Python 3, standard library only | Present on nearly every developer machine and CI image | Arbitrary-precision `int` and `fractions.Fraction` built in | None |
| TypeScript on Node.js | Common, but needs Node plus a runner or compile step | `BigInt` only; no rational type | npm toolchain and lockfile |
| Go | Fast; not present on most machines that aren't Go machines | `math/big` | Go toolchain |

Several generators depend on exact integer and rational arithmetic: integer
edges up to and beyond 128 bits, and binary floating-point rounding midpoints.
Python provides that with no dependencies. The volumes are modest (aggregate
output caps of 16–256 MiB per tier), and streamed Python generation handles
them in seconds.

## Decision

1. **Corpus tools and generators are Python 3, standard library only.** The
   command interface is a single entry point, `python3 tools/corpus.py
   <subcommand>`.
2. **Minimum version is Python 3.9**, the oldest `python3` that still ships
   with a current major OS. Code does not use features newer than 3.9, such
   as `match`, `tomllib`, or the `X | Y` union syntax evaluated at runtime.
   CI tests the floor and a current release.
3. **Determinism rules for generated bytes:**
   - No `random`, `secrets`, `hash()`, `uuid`, ambient time, locale, or
     environment input. Where pseudo-randomness is needed, generators use a
     specified, in-tree PRNG (SplitMix64), seeded explicitly.
   - Iteration order never depends on set ordering.
   - Files are written in binary mode with explicit encodings and newlines.
   - Canonical manifests use a **constrained JSON subset** whose canonical
     form is RFC 8785 (JCS) output by construction. Ordinary Python JSON
     serialization alone is not JCS, so the subset and its serializer are
     specified together:
     - Values are objects, arrays, strings, `true`, `false`, `null`, and
       integers. There are no floating-point numbers. Numeric fixture values
       that need exactness, or that fall outside the integer range, are
       written as strings.
     - Integers lie in the interoperable range −(2^53 − 1) to 2^53 − 1
       (RFC 7493), so every JCS implementation serializes them identically.
     - Strings are valid Unicode: lone surrogates are rejected on input, and
       JSON escapes that decode to a lone surrogate are rejected too.
     - Object member names are unique.
     - The serializer sorts members by the UTF-16 code-unit order of their
       names, as JCS requires, not by Python's code-point order. The two
       differ for names containing characters above U+FFFF.
     - Output is UTF-8 with no insignificant whitespace. Characters are
       escaped as JCS specifies: the short escapes, `\u00XX` for other
       control characters, and every other character emitted literally.
     - The validator rejects metadata outside the subset. Tests check the
       serializer against published JCS test vectors that fall within the
       subset, and against cases where UTF-16 and code-point order differ.
4. **No Python package manager, ever.** There is no `requirements.txt`,
   `pyproject.toml` dependency list, virtual environment, or installer step
   (pip, uv, poetry, or otherwise). The tools are plain scripts run directly
   by `python3`.
5. **Full JSON Schema validation is a maintainer and CI check, done with an
   established external validator run as a pinned binary.** It is never
   re-implemented in Python and never installed through a Python package
   manager. The admission-critical checks are implemented in the stdlib tool,
   so a consumer can verify a pin without installing anything:
   classification, provenance presence, hashes and lengths, safe paths,
   duplicate JSON keys, and unknown schema versions.
6. **Metadata and recipes are JSON, not TOML or YAML.** The 3.9 floor has no
   TOML reader, and a YAML corpus must not need a YAML parser to read its own
   metadata.
7. **The CLI stays a single stdlib `argparse` entry point** while it fits that
   shape. If it outgrows one (plugins, rich output, configuration layering),
   the replacement is chosen by a new decision record from established
   lightweight CLI templates, not grown ad hoc.
8. **Adding another language** for a generator (for example, Go for a
   throughput-bound stress recipe, or TypeScript where a JavaScript-specific
   behavior must be produced natively) requires a new decision record backed
   by measured need. No language-binding projects are created here.

## Consequences

- Corpus users need only `python3` to validate, hydrate, and verify.
- Typing and ergonomics are limited by the 3.9 floor, and the code accepts
  that.
- Two validation layers exist. The stdlib layer is the gate a consumer can
  always run. The schema-validator layer catches structural drift in CI. A
  case passing one and failing the other is a bug.
- Keeping exact arithmetic in-language lets an independent reviewer check
  numeric oracles against Python's integer and rational semantics, without
  involving the floating-point parser under test.
